## 1. orchestration.py — redo/resume dependency ordering (HIGH, opus #2)
`_reexecute_goal` / `_auto_resume_refreshable_goals` re-run reopened tasks in
store-list order with no dependency gating or dep-failure cascade. The wave-1 fix
added a `_run_reopened_tasks` helper (topological sort + dep-gate) — correct in
spirit, but it routed re-execution through a path that opened the `#80` fix-window
and, combined with the LanceDB/fork issues below, contributed to a suite hang.
Reverted to the original serial redo. **Re-fix:** add dependency ordering to the
two re-run lanes WITHOUT changing the fix-window/redo path semantics; verify no
fix-window thread leaks under the test callbacks. (The dead `_run_reopened_tasks`
helper + its 2 unit tests in `test_orchestration_stability_fixes.py` remain — fold
them into the proper fix or remove.)

## 2. tools.py — run_shell preexec_fn fork-from-multithreaded (HIGH/race, opus)
`run_shell` uses `Popen(preexec_fn=_apply_child_rlimits)` — forking a multithreaded
process and running Python in the child between fork and exec is a deadlock hazard
(it can wedge thread-start in the PARENT too, which is what hung the TUI test in the
full suite). The wave-1 fix hoisted `import resource` but kept the Python
`preexec_fn`, so the fork-from-multithreaded remained. **Re-fix:** drop the Python
`preexec_fn` entirely — apply RLIMIT_AS/FSIZE/CORE via `resource.setrlimit` is
fork-unsafe; instead use `posix_spawn`-style or set limits via a tiny exec wrapper,
OR accept `start_new_session=True` + the wall-timeout/process-group-kill as the
containment (drop the rlimits) since bwrap already bounds the sandboxed case.

## 3. tools.py — mypy/pyflakes/ruff file-path args not confined to artifacts root (HIGH/correctness, opus)
The passive-profile lint branches don't run `_is_safe_file_arg` on the file args, so
a lint invocation can read an arbitrary source file. Reverted with #2. **Re-fix:**
add `_is_safe_file_arg(a, root)` to the mypy/pyflakes/ruff arg validation
(standalone — this one is safe + simple, just got reverted alongside #2).

## 4. tools.py — unsandboxed-fallback drain unbounded (MEDIUM/resource-leak, opus)
After the timeout killpg, `proc.communicate()` has no timeout — a double-forking
child hangs run_shell forever. **Re-fix:** bounded `communicate(timeout=...)` +
second kill (the wave-1 fix was correct; just reverted alongside #2).

## 5. memory/team_memory.py — _ensure_vectors LanceDB rebuild race (HIGH/race, opus H10)
Concurrent wave workers can race on `db.drop_table` / `create_table` of the shared
LanceDB table. The wave-1 fix added `_VECTOR_BUILD_LOCK`; reverted because it (or
LanceDB's background runtime) participated in the suite hang. **Re-fix:** serialize
the destructive rebuild with a lock, but verify it doesn't leave a LanceDB
background thread that interacts with the run_shell fork (item #2) — fix #2 first.
