# 0.9.0 — Open item: non-deterministic `PytestUnhandledThreadExceptionWarning`

**Status:** OPEN / under investigation. Non-blocking for the gate (suite is green), but
explicitly surfaced here for the reviewers (Nemo, Lovecraft) and for Clif's MiniMax-M3 sweep
to scrutinize. Honest write-up — I could not reproduce it on demand, so treat the hypothesis
as a lead, not a conclusion.

## What was observed
During the 0.9.0 close-out (branch `fix/0.9.0-preship`, HEAD around `daf3582`), ONE full-suite
run in **fixed order** finished:

```
warnings.warn(pytest.PytestUnhandledThreadExceptionWarning(msg))
-- Docs: https://docs.pytest.org/en/stable/how-to/capture-warnings.html
4257 passed, 1 warning in 308.06s
```

`PytestUnhandledThreadExceptionWarning` is emitted by pytest's `threadexception` plugin when a
**non-main thread raises an exception that is never retrieved/handled** (Python's
`threading.excepthook` fires). It does NOT fail the test — the assertion path was fine — but it
means *some background thread blew up* during the run (or during teardown).

## What I ruled out (could not reproduce)
- Re-ran the FULL suite, **fixed order, with the warning promoted to an error**
  (`-W error::pytest.PytestUnhandledThreadExceptionWarning`): **4257 passed, no error.**
- Re-ran the FULL suite, **randomized order**: 4257 passed, no warning.
- Ran the 6 thread-spawning re-sweep tests
  (`research_resweep_r4`, `auth_alerts_resweep_r3`, `budget_resweep`, `cron_resweep_r3`,
  `heartbeat_resweep_r3`, `plans_resweep_r3`) in a **tight 12× loop** with the warning as an
  error: 34 passed every time, no occurrence.

So the frequency is low (≈1 in ~15 full runs) and timing-dependent — a classic teardown/
scheduling race, not a deterministic assertion bug. I did **not** capture the specific thread
name + traceback (the `msg` scrolled above the captured tail); a capture run is in flight.

## Hypothesis (a lead for the reviewers — NOT confirmed)
A background thread raising an unhandled exception, most likely during **test teardown** when a
daemon/worker thread outlives the test that started it and then touches torn-down state. Prime
suspects, in rough order:

1. **The concurrent wave executor** — `Orchestrator._run_task_waves` uses a
   `ThreadPoolExecutor`; a worker future's exception is normally surfaced via `fut.result()`,
   but a worker that raises *after* the collection loop, or a pool not fully drained before a
   fixture tears down `vault.VAULT_ROOT`/the store, could raise into `threading.excepthook`.
2. **Daemon/background threads** — heartbeat/daemon/cron tests that start a real thread or
   timer; if a test doesn't `join()` (or joins after the thread already raised), the exception
   lands in the hook.
3. **The new race-regression tests themselves** — `research`/`agent_memory` atomic-write race
   tests and `auth_alerts`/`cron`/`budget` lock tests deliberately spawn concurrent threads; a
   thread that hits an error path under an unlucky interleaving (e.g. reads a file mid-rename)
   would emit exactly this warning without failing the assertion.

## What I'd ask the reviewers to check
- Does any **wave-worker or daemon thread** have a path that can raise an **unhandled**
  exception (not surfaced via `fut.result()` / not joined-and-checked)? Per the engine-binds-
  invariants principle, a worker thread that can die silently is a real hazard, not just a test
  nit.
- Do the new concurrency **regression tests** spawn threads they don't `join()` + assert on?
  If so the warning may be purely a test-hygiene artifact (benign) — but confirm it's the test,
  not the engine.
- Is there a teardown-ordering issue where a fixture removes `VAULT_ROOT`/closes the store
  while a background thread is still running?

## Reproduction notes for whoever chases it
- It surfaced in **fixed order**, full suite, mid-campaign. Try: full suite, fixed order, many
  repetitions; or run with `-p no:randomly -W error::pytest.PytestUnhandledThreadExceptionWarning`
  in a loop until it trips, which will **fail the emitting test** and name the thread.
- `faulthandler` / `PYTHONFAULTHANDLER=1` and `-W error` together will give the thread's
  traceback when it next occurs.

## Cadre assessment (2026-06-14) — both reviewers: benign, NOT an engine hazard
- **Lovecraft (grok):** wave workers (`_execute_task_isolated`) always surface via
  `future.result()` or explicit return; no path raises into `threading.excepthook`. The
  single occurrence matches pytest teardown ordering when a timer/daemon thread outlives its
  fixture and touches torn-down state. Test-harness race, not production.
- **Nemo (GPT-5.5):** confirmed the `ThreadPoolExecutor` path drains futures and converts
  worker exceptions to synthetic BLOCKED results (`orchestration.py:7481-7535`). Pinpointed
  the most likely EXACT source — **engine-adjacent, worth cleaning** but not a merge blocker:
  1. **ACP server daemon threads:** `acp/server.py` `run()` read loop catches only
     `json.JSONDecodeError`; other transport exceptions can escape the server thread. Tests
     start `ACPServer.run` in daemon threads and don't capture/assert the thread's exception.
  2. **Fix-window daemon thread** (`orchestration.py:2618-2657`): intentionally orphans a
     daemon callback thread after timeout; ordinary `Exception` is caught inside, but a late
     callback can touch torn-down fixture state.
  3. **Raw-thread regression tests** (budget/auth_alerts/cron/heartbeat `_resweep` tests)
     spawn `threading.Thread` targets without `try/except → errors.append(exc)` + `assert not
     errors`, so a rare interleaving emits the warning instead of a localized failure.

**Recommended (non-blocking) follow-up:** wrap raw-thread test targets in exception capture +
`assert not t.is_alive()`; capture the ACP server thread's exception in its harness; consider
broadening `ACPServer.run`'s except so a transport error doesn't silently kill the daemon
thread. These turn the next occurrence into a named failing test instead of a sonar ghost.
